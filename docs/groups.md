# Groups & shared progress

Groups exist for **shared accountability, not competition** (spec §46–48). A group answers
"How are the people in my group doing today?". It never ranks members, and it never
answers "who is best". There are no leaderboards, scores, points, badges, streak
competitions, comparisons or group averages.

Code lives in `src/features/groups`. The database layer is
`supabase/migrations/20260927000600_groups.sql`, extended by
`20261006000100_groups_feature.sql`.

## Model

| Table               | Key fields                                                                                                  |
| ------------------- | ----------------------------------------------------------------------------------------------------------- |
| `groups`            | name (1–60), description (≤ 500), `code` (one per group, immutable), `creator_id`, `is_active`/`deleted_at` |
| `group_memberships` | `group_id`, `user_id`, `role`, `joined_at`, `left_at`, `removed_by`, `is_active`                            |

- **Roles:** the spec's `MEMBER`, `LEADER` and `ADMIN` (labelled Member, Group leader, Group
  admin).
  - They are per group and independent of global RBAC. An app ADMIN is not a group admin,
    and a user can hold different roles in different groups.
- **Code:** 8 characters, generated by the database, from an alphabet without look-alikes
  (no 0/O, 1/I/L).
  - It is unique across all groups, never regenerated (Phase 1), and never taken from the
    browser.
  - Typing is forgiving: case, spaces and dashes are ignored, and it's shown as `ABCD-EFGH`.
- **History:** memberships are never reactivated or deleted. Leaving sets `is_active =
false` and `left_at`; a removal also records `removed_by`. Rejoining creates a new row.
  Groups are soft-deleted.

## Actions (server-side functions)

Every action is a `SECURITY DEFINER` function that acts for `auth.uid()`. Nothing the browser
sends can name another creator, member or privilege.

| Function                                   | Who                   | Behaviour                                                                                   |
| ------------------------------------------ | --------------------- | ------------------------------------------------------------------------------------------- |
| `create_group(name, description)`          | any active user       | Creates the group, its code and the creator's `ADMIN` membership in one transaction         |
| `preview_group(code)`                      | any active user       | The "Confirm group" step: name, description, member count. An unknown code returns nothing  |
| `join_group(code)`                         | any active user       | Joins immediately. Already a member = no change. Invalid or closed code = one generic error |
| `leave_group(group)`                       | any member            | Ends access at once                                                                         |
| `remove_group_member(group, user)`         | group `ADMIN` only    | Ends that member's access at once. Leaders and members can't remove                         |
| `set_group_member_role(group, user, role)` | group `ADMIN` only    | Appoints a leader, or another admin (e.g. before leaving)                                   |
| `get_my_groups()`                          | the user              | Their active groups: name, description, code, their role, member count, first viewable date |
| `get_group_members(group)`                 | members of that group | Roster only: user id, display name, group role, join time                                   |
| `get_group_member_day(group, date)`        | members of that group | The shared daily summary (below)                                                            |

**Admin continuity** (a decision, since the spec says only "any member may leave"):

- A group always keeps an admin while it has members. The only admin can't leave or step
  down while others remain: they first make another member an admin (Members → role). The
  UI explains this instead of offering a Leave button.
- The last member leaving closes the group (`is_active = false`). Its code no longer works.
  No admin is ever created automatically.
- The same rule is enforced by the membership trigger, so direct table updates can't
  bypass it.

Group deletion as a workflow is not in the spec and isn't built.

## Privacy boundary

Members **never** read each other's tables. RLS on meals, workouts, steps, weight, InBody,
profiles, goals, cycles and snapshots is unchanged: own rows, assigned managers, app
admins. The only cross-user read is `get_group_member_day()`, which returns exactly:

| Field                                 | Source                                                                                                                                                                                                       |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `name`, `group_role`                  | display name and group role                                                                                                                                                                                  |
| `calories`, `protein_g`               | logged meal-item snapshots for that date. This is the same aggregation as Progress and recommendations (`recommendation_daily_nutrition`); deleted meals and items are excluded. Nothing logged gives `null` |
| `calories_target`, `protein_target_g` | the target **in force on that date**: the date's snapshot, otherwise the covering (non-replaced) cycle's final targets. Never today's target applied to the past                                             |
| `steps`                               | the active step entry. None gives `null`                                                                                                                                                                     |
| `steps_target`                        | always `null`: there is no step goal in Phase 1. None is invented, and `0 / 0` is never shown                                                                                                                |
| `workout_logged`                      | whether any non-deleted workout exists that day (a workout day; several workouts still count as one)                                                                                                         |

**Never returned:** weight, body fat, muscle mass, InBody, height, age or date of birth,
gender, BMR, phone, calculation inputs, goals or objectives, recommendations or AI data,
meals or food items, workout details.

Group actions write only group structure to the audit log (names, roles, dates), never
member data.

**Who can see what:**

- The function answers only for an active member of an active group, and only about that
  group's active members with active accounts.
- Membership in one group grants nothing in another. Changing `group_id`, `user_id` or the
  date can't reach data outside this rule.
- Future dates are refused.

**History rule** (spec §47–48: "where permitted"; leaders get "limited historical access"):

- A member's data is shown only from the day **that member** joined.
- A `MEMBER` sees dates from their **own** join day onward.
- A `LEADER` or `ADMIN` also sees the time before they joined, back to the group's creation.
  Each member is still shown only from their own join day. This is the leader's extra
  access, and there is nothing else: no management rights and no private data.
- The date picker starts at `history_from` from `get_my_groups()`.

**Former members:**

- After leaving or removal, a member immediately loses every group read: roster, shared
  days (including past dates) and the group row itself. This includes a creator who left.
- Their own records are untouched, and they stay signed in.
- Their data disappears from the group at once. On rejoining, their history restarts at the
  new join day.

## UI

- **`/groups`:**
  - compact cards showing name, description, member count and your role;
  - Create group, and Join group (enter code → confirm group → join);
  - the empty state offers both.
  - After creation, the code is shown with a Copy button and a link to the group.
- **`/groups/:groupId`:**
  - Header: member count, your role and Leave group, plus the join code with Copy.
  - Date: Today by default. The shared day picker (`DayNav`) never goes past today or
    before your first viewable date, and `?date=` is supported.
  - One card per member: calories and protein as `actual / target`, steps, and Workout done
    or No workout logged. Missing values show `—`, never zeros, with no success/failure
    colours.
  - Members: roster with join dates. A group admin also gets a role selector and Remove
    (with confirmation).
- **Navigation:** the existing Groups entries; `/groups/:id` highlights Groups.
- **Data refresh:**
  - Group queries live under `['groups', userId]`. Joining, leaving, removals, role changes
    and the user's own meal, workout and steps changes invalidate them.
  - Group and date are part of every key, so switching never shows the previous
    selection's data.

## Tests

- **Database:** `supabase/tests/database/09_groups.test.sql` (66 assertions) covers:
  - creation and authorization;
  - join by code, invalid codes and duplicates;
  - cross-group isolation (malicious `group_id`);
  - private tables and function columns;
  - target by date (snapshot, cycle fallback, later cycle), deleted records, the history
    rule, removal and leave permissions;
  - admin continuity, former-member denial, rejoin, closed groups, inactive accounts and
    audit.
- **Integration:** `tests/integration/groups.test.ts`, as signed-in users on the local
  stack.
- **Unit and component:** `src/features/groups/lib/groups-logic.test.ts` and
  `src/features/groups/pages/groups-pages.test.tsx`.

## Limitations

- No step goal exists yet, so steps show without a target.
- Leaders' extra access is limited to history. No other leader features exist in Phase 1.
- There is no rate limiting on code attempts beyond the code space (31⁸ combinations).
